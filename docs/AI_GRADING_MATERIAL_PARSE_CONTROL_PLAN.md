# AI 批改材料解析控制与拆题失败修正

> 文档版本：`v1.1`
> 日期：2026-09-12
> 状态：v1.0 已通过 PR #20 合并部署；v1.1 拆题输出契约修正已批准并实施，待交付
> 开发基线：`origin/main@b1583bef0db03d49eeb0d801e024c68e18ad3f7b`

## 1. 原始问题与目标

教师选择作业题目或参考答案后，页面会立即上传并开始材料解析，没有核对文件和主动开始的控制点。一次选择多份文件时，教师无法在资源消耗前纠正选择。

同时，生产环境显示“AI 拆题失败，请检查模型配置”，但 2026-09-12 的真实日志表明实际错误是上游模型服务返回 HTTP 503。目标是恢复教师对解析时机的控制，并让拆题失败反馈准确说明失败阶段、数据保存状态和下一步操作。

## 2. 已确认事实

- 题目和答案文件输入此前直接调用上传接口；服务端收到文件后在后台异步、并行解析，前端轮询材料状态。
- 单次材料上传最多 20 个文件、每个文件最多 4 MiB。本次不降低数量，也不把解析改成串行。
- 故障任务只有 1 份题目和 1 份答案；两份材料均为 ready、无解析警告，共 27 个内容块和约 1453 个字符。
- 19:16 左右四次拆题请求均记录 `MODEL_REQUEST_FAILED:503`。第一次约 70.6 秒后失败，随后三次约 0.5–1.3 秒内失败。
- 前端未识别该错误码，落入“请检查模型配置”的默认文案；材料和模型配置不是本次已知根因。
- 日志没有记录上游响应正文，因此只能确认服务暂时不可用，不能把排队、维护或网关过载中的任一项断言为事实。

## 3. 产品与实现决策

1. 文件选择只进入浏览器待解析区，不自动上传或解析。
2. 题目和答案共用一个“上传并开始解析”主操作；点击后仍按现有机制并行上传、后台异步解析和轮询状态。
3. 待解析区显示文件数量、文件名、清除入口和替换影响；重新解析对应材料会使已有拆题结果失效。
4. Compact 下主按钮占满可用宽度，Wide 下保持紧凑；主要操作和清除入口高度不低于 44px，调整窗口不丢失待处理文件和错误状态。
5. AI 拆题按钮只在题目、答案均已解析时可用。
6. 服务端把上游 401/403、429、502/503/504、其他拒绝和输出结构错误映射为不同稳定错误码。
7. 页面保留持久失败卡片和重新拆题入口；失败时明确材料已保存、本次未生成拆题结果。
8. 本次不自动重试模型请求，避免外部服务不可用时连续产生无意义调用。

- `src/features/grading/GradingWorkflow.tsx`：待解析文件状态、统一开始按钮、响应式布局、拆题可用条件及持久错误反馈。
- `server/routes/gradingTasks.ts`：拆题模型错误分类与 HTTP 状态语义。

- `docs/WEB_PRODUCT_PHASE1_PLAN.md`、`docs/EMPTY_WORKSPACE_CLASS_FIX_PLAN.md`：校正 PR #11 和生产 schema v11 的实际状态。
- 本文：记录问题、证据、决策、范围和交付状态。

## 5. 风险与取舍

- 文件在点击开始前只存在于当前浏览器选择状态，刷新页面后需要重新选择；这是避免未经确认上传和解析的直接取舍。
- 并行解析保留现有效率，也保留单次多文件对本机和 OCR 服务的瞬时压力；当前最多 20 个文件且用户明确接受该边界。
- 上游 503 无法由本地代码消除。本次修正可观察性和恢复入口，不把外部服务故障伪装成已经解决。
- 新材料仍会替换同类型旧材料并使旧拆题结果失效；页面在执行前明确告知，不改变现有数据语义。

## 6. 检查与授权边界

按用户要求只执行代码审查、TypeScript 静态检查、部署所需生产构建和 `git diff --check`；不调用真实 OCR/AI，不执行完整测试矩阵或浏览器验收。网站体验由用户在合并部署后验证。

v1.0 实施当时只授权本地提交，后续经用户单独授权后通过 PR #20 合并并从母文件夹稳定 `main` 部署；COS TODO 补记已一并纳入。

## 7. v1.1 真实拆题失败根因

PR #20 部署后，用户在正式网站两次触发拆题。请求均到达正式服务，分别约 63 秒和 74 秒后返回 502。模型已返回可解析 JSON，但第 2 题的 `knowledgeCandidates` 是字符串数组，而服务端契约要求 `{ nodeId, nodeName, confidence }` 对象数组，整份输出因此在业务收敛前被拒绝。

因果链为：

1. Prompt 只展示了空的 `knowledgeCandidates: []`，没有非空对象示例。
2. 拆题请求未使用项目已有的 `response_format/json_schema/strict` 机制，只依赖自然语言提示。
3. 服务端在可恢复的知识点字段被处理之前就严格解析整份结果，一个次要字段错误放大为整份拆题失败。
4. 正式环境使用第三方 OpenAI 兼容网关；其对当前模型严格 JSON Schema 的完整支持仍需由用户的真实网站验收确认。

## 8. v1.1 实施决策

1. 拆题请求复用 `firstSectionAnalysisJsonSchema`，启用 `response_format: json_schema` 和 `strict: true`。
2. Prompt 增加非空知识点对象示例，明确禁止字符串数组。
3. 仅对 `knowledgeCandidates` 执行允许列表式恢复：移除非法候选项，并向对应题目写入人工复核原因；不猜测节点、不伪造置信度。
4. 题干、答案、题号、分值和证据引用等核心字段仍严格校验；异常时不入库。
5. 记录恢复的题号和候选数量，不记录完整题目、答案或模型原始输出。
6. 不增加自动重试；兼容网关若拒绝严格 Schema，保留失败并继续显示可操作错误，不二次计费。

## 9. v1.1 检查边界

- 按用户约定只运行定向单元测试、TypeScript、生产构建和差异检查；不调用真实 AI/OCR。
