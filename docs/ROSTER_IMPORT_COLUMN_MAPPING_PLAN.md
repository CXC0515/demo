# 学生名册列字段匹配与断线保护方案

## 1. 原始问题与目标

教师上传或粘贴学生名册后，现有界面以“表格列名 → 学生字段”的方向展示匹配，示例与说明不足，容易把仅代表表格行序的“序号”误选为“学号”。预览请求遇到 Cloudflare Tunnel 502 时，界面还会保留旧预览与确认按钮，产生误操作风险。

本次目标：

1. 将匹配界面改为“左侧学生字段，右侧选择表格列名”。
2. 保留真正的“学号”字段；“序号”默认忽略，不自动当作学号。
3. 明确自动匹配和人工纠正的关系，并让必填字段可见。
4. 阻止同一表格列被重复用于多个学生字段。
5. 预览短暂断线时安全重试；失败后撤销失效预览并禁止确认。
6. 学号与姓名指向不同现有学生时，不覆盖任何学生。

## 2. 已确认事实、产品决策与边界

### 已确认事实

- 2026-09-09 15:52–15:53，Express 收到的四次导入预览均返回 HTTP 200。
- 随后 Cloudflare Tunnel 的两条 QUIC 连接发生超时；502 请求未到达 Express。
- 同一时段没有最终导入请求，截图中的 53 条预览未因此写入数据库。
- 当前后端不会把“序号”自动识别为学号，但会把含义模糊的“编号”识别为学号。
- 当前预览失败不会清除旧预览，确认按钮仍可能可用。
- 数据库中的 `student_no` 是系统的真实学号字段，本次不改变其含义或结构。

### 已确认产品决策

- 左侧固定列出学生字段，右侧选择对应的表格列名。
- 学号和学生姓名为新增学生必填字段。
- `序号`只是来源表格中的普通列名，默认不导入。
- 明确的 `学号`、`学生学号`、`学生编号`可自动匹配为学号；含义模糊的`编号`不自动匹配。
- 教师可以手动调整任何列匹配。

### 本次边界

- 不修改 SQLite 表结构，不迁移真实数据。
- 不把产品其他页面的“学号”改为“序号”。
- 不自动重试最终写入操作。
- 不在本次代码修改中改变 Cloudflare Tunnel 或代理配置；隧道稳定性作为独立运维问题处理。

## 3. 最短实施路径

### 前端匹配界面

- 表格左列固定展示学生字段，右列选择来源表格列名。
- 自动匹配成功的字段预先选中；未匹配字段显示“不导入”。
- 已被其他字段使用的来源列不能再次选择。
- 示例使用“序号、学号、学生姓名、性别”，并明确序号默认忽略。
- 匹配变化后重新生成预览；预览准备完成前确认按钮不可用。

### 断线与失败状态

- 预览接口遇到网络错误或 502/503/504 时自动重试一次。
- 仍失败时保留输入与匹配草稿，清除旧预览并禁用最终确认。
- 错误信息说明影响范围与恢复动作，不暴露 `HTTP_502`。
- 最终导入失败不自动重试；尝试刷新名册后提示教师先核对结果。

### 后端识别与保护

- `序号`和含义模糊的`编号`不自动映射为学号。
- 自动推断时同一学生字段只采用第一个明确匹配列。
- 学号与姓名分别指向不同已有学生时，返回冲突并拒绝该行。

## 6. 风险与取舍

- 收紧“编号”的自动识别可能使旧表格少一个自动匹配，但教师仍可手动选择“学号”，安全性高于猜测。
- 一次自动重试只能缓解短暂隧道中断，不能解决学校网络封锁 Cloudflare 的根因。
- 学号与姓名不一致时选择拒绝而非自动改名，牺牲少量便利以避免错改学生身份。
- 最终写入请求不自动重试，避免响应丢失后产生重复操作。
